# 海鲜 X 光分拣系统技术方案与产品需求说明

版本：V1.2  
日期：2026-06-30

## 1. 文档目的

本文用于同步当前项目的真实技术路线和产品功能边界，覆盖：

- 产品目标与交付范围；
- 当前 WPF HMI、LocalApi、Runtime、DeviceHost、YOLO FastAPI 服务的分工；
- 海鲜产品、模型、通道、检测任务、检测记录、人工复核、设备告警等数据模型；
- X 光图像数据源配置；
- 生产检测与离线检测差异；
- 后续真实硬件接入和软件维护方向。

本文以当前代码和当前甲方可见功能为基准，不再把暂停中的 Electron/Vue 原型作为主交付口径。

## 2. 系统背景

系统面向 Windows 工控机上的海鲜 X 光分拣场景，核心硬件包括：

- X 光光源；
- X 光探测器；
- 传送带；
- 剔除设备；
- PLC 或设备控制器。

系统通过 X 光图像采集、YOLO 推理、后处理、统计记录、告警联锁和剔除控制，实现对贝类海鲜的质量检测和异常剔除。

典型海鲜产品包括：

- 油蛤；
- 花蛤；
- 美贝；
- 后续可扩展其他海鲜产品。

## 3. 当前产品目标

### 3.1 当前交付目标

当前阶段目标是形成一套可展示、可联调、可持续开发的 Windows 工控机 HMI 软件：

- 首页作为生产常驻页面；
- 管理员可维护产品、模型、通道、硬件、剔除、安全和软件维护配置；
- 操作员可启动/停止机器，查看实时 X 光图像、识别结果、统计数据；
- 系统支持 X 光相机数据源和本地图片目录数据源；
- 本地图片目录模式用于离线检测分析，不触发真实剔除设备；
- 数据中心可按海鲜产品和检测任务查看统计；
- 人工复核页面可对异常集合进行模型效果评估。

### 3.2 后续生产化目标

后续生产化阶段重点包括：

- 对接真实 X 光探测器 SDK；
- 对接 PLC 和剔除控制器；
- 完成剔除时序、编码器、距离和像素比例标定；
- 完善红色硬件联锁告警；
- 完善报表、追溯、更新包安装和回滚；
- 增加生产批次、班次、审计日志和长期数据清理策略。

## 4. 软件模块分层

### 4.1 当前模块

| 模块 | 当前职责 |
| --- | --- |
| `Domain` | 实体、枚举、运行数据源、检测任务、人工复核、硬件设备、告警、软件版本等核心模型 |
| `Application` | 产品/模型/通道规则、运行协调、统计聚合、人工复核、软件版本、设备告警等业务服务 |
| `Infrastructure` | SQLite/本地持久化、预览图生成、数据源存储、设备/告警存储等基础设施 |
| `LocalApi` | WPF HMI 调用的本地 ASP.NET Core API |
| `Runtime` | 图像源、推理、定位、剔除控制和运行 worker 抽象 |
| `DeviceHost` | 设备状态和剔除控制相关 worker/适配宿主 |
| `HMI` | 当前交付 WPF 工控机桌面界面 |
| `ElectronHmi` | 暂停中的 Electron/Vue 原型，仅保留参考 |
| `FastAPI YOLO 服务` | 常驻加载模型，执行 YOLO 推理和 Python 后处理逻辑 |

### 4.2 当前运行链路

```text
WPF HMI
  ↓
LocalApi
  ↓
RuntimeCoordinator / RuntimeDashboardService
  ↓
RuntimeDataSourceConfig
  ├─ XrayCamera
  └─ LocalImageDirectory
  ↓
当前启用通道
  ↓
产品标签映射 + 模型权重 + 通道阈值
  ↓
FastAPI YOLO 服务
  ↓
InspectionRecord / DetectionSession / ManualReviewRecord
  ↓
首页统计 / 数据中心 / 人工复核 / 剔除控制
```

## 5. 核心数据模型

当前系统已经不再只有“产品、模型、通道”三个表。产品、模型、通道仍是配置核心，但运行和生产统计已经扩展出检测任务、检测记录、人工复核、设备、告警和软件维护等对象。

### 5.1 海鲜产品 `SeafoodProduct`

用途：定义业务产品、类别标签标准和产品级推理配置。

关键字段：

- `Code`：产品编码。
- `Name`：产品名称。
- `IsEnabled`：是否启用。
- `ClassesFilePath`：类别标签文件路径，典型文件为 `classes.txt`。
- `LabelMapJson`：模型类别编号到业务性状的一一映射。
- `PredictConfigPath`：产品级 YOLO 配置路径。

规则：

- 新增产品必须导入类别标签文件。
- 新增产品必须完成类别标签与业务性状的一一映射。
- 编辑产品时不要求每次重新导入类别标签文件；若标签顺序和性状未变，可保留原映射。
- 产品至少包含一个正常项和一个缺陷项。
- 产品必须且只能有一个正常项。

### 5.2 海鲜性状 `SeafoodTrait`

用途：描述某个产品的业务性状。

关键字段：

- `Name`：性状名称，例如 `正常`、`碎壳`、`泥包`、`空壳`。
- `IsNormal`：是否为正常项。
- `SortOrder`：排序。
- `IsEnabled`：是否启用。

### 5.3 模型 `ModelVersion`

用途：管理 YOLO 模型权重和版本。

关键字段：

- `SeafoodCategoryId`：所属海鲜类别/产品关联维度。
- `Version`：模型版本编号。
- `SourceWeightPath`：源权重文件路径。
- `Notes`：备注。
- `Status`：软删除状态，仅区分正常（0）与已删除（9），不表示启用、停用或回滚。
- `CreatedAt`：创建时间。

当前约定：

- 模型版本编号用于展示和追踪，不作为业务判断主键。
- 版本编号由系统按产品前缀和序列号生成，例如 `YG-MV-001`。
- 标签映射以产品层 `LabelMapJson` 为准，模型不重复维护标签映射。
- 删除模型时保留数据库记录并标记为已删除；常规查询、通道绑定和运行流程不返回已删除模型。
- 置信度阈值当前由通道或产品配置决定，不作为模型主字段。

### 5.4 通道 `ChannelConfig`

用途：定义当前运行使用的产品、模型和推理参数。

关键字段：

- `ChannelNo`：通道序号，保留用于硬件/剔除位映射。
- `Name`：通道名称，界面主要识别字段。
- `SeafoodProductId`：绑定海鲜产品。
- `ModelVersionId`：绑定模型。
- `ModelPath`：模型权重路径。
- `ConfidenceThreshold`：置信度阈值。
- `IsEnabled`：是否启用。
- `LastRuntimePredictConfigPath`：最近一次运行配置副本。
- `LastRuntimeOutputDirectory`：最近一次运行输出目录。
- `CameraToEjectDistanceMillimeters`：相机到剔除位距离。
- `MillimetersPerPixelY`：纵向像素比例。
- `SoftwareLatencyMilliseconds`：软件延时补偿。
- `ActuatorDelayMilliseconds`：执行器延时补偿。
- `HorizontalLaneMappingJson`：横向剔除位映射。

当前收缩原则：

- 传送带速度不是通道字段，属于整机运行参数。
- X 光电压、电流不是通道字段，属于硬件/整机默认参数。
- 剔除动作方式和剔除设备参数应进入剔除设置。
- 当前业务按单一当前启用通道设计，机器运行中不允许切换通道。

### 5.5 数据源配置 `RuntimeDataSourceConfig`

用途：定义机器启动后图像从哪里来。

模式：

- `XrayCamera`：生产 X 光采集模式，允许硬件剔除。
- `LocalImageDirectory`：本地目录离线检测模式，不允许硬件剔除。

关键字段：

- `Mode`
- `LocalDirectoryPath`
- `FrameIntervalMilliseconds`
- `ImageCount`
- `CurrentIndex`
- `IsHardwareExecutionEnabled`
- `Status`

### 5.6 检测任务 `DetectionSession`

用途：表示一次生产检测或离线检测任务。

关键字段：

- `SessionCode`
- `ChannelId`
- `ProductId`
- `ModelVersionId`
- `StartedAt`
- `EndedAt`
- `Status`
- `DataSourceMode`
- `IsHardwareExecutionEnabled`

统计口径：

- 首页只展示当前检测任务数据。
- 数据中心按检测任务和海鲜产品聚合历史数据。

### 5.7 检测记录 `InspectionRecord`

用途：表示单张 X 光图片的检测结果。

关键字段：

- `DetectionSessionId`
- `ImagePath`
- `CapturedAt`
- `Detections`
- `EjectCommands`
- `IsRejected`
- `IsTimedOut`

统计口径：

- 海鲜总数 = 检测框数量。
- 正常数 = 正常类别检测框数量。
- 异常数 = 非正常类别检测框数量。
- 真实剔除命令数 = `EjectCommands.Count`，仅生产模式可能大于 0。

### 5.8 人工复核 `ManualReviewRecord`

用途：对异常集合进行人工复核，用于模型能力评估。

关键字段：

- `DetectionSessionId`
- `InspectionRecordId`
- `DetectionId`
- `ModelLabel`
- `HumanLabel`
- `Judgement`
- `Reviewer`
- `Notes`
- `ReviewedAt`

判断类型：

- `ConfirmedAbnormal`：确认异常。
- `FalsePositive`：正常误检。
- `RelabeledAbnormal`：类别修正。

当前只复核异常集合，不覆盖未剔除集合抽检，因此不计算严格召回率。

### 5.9 硬件设备与告警

关键对象：

- `HardwareDevice`
- `HardwareSignalStatus`
- `AlarmEvent`
- `RuntimeSnapshot`

关键硬件：

- X 光光源；
- X 光探测器；
- 传送带；
- 剔除设备；
- 控制器/PLC。

规则：

- 关键硬件异常应触发红色告警。
- 严重硬件故障时系统进入不可正常运行状态。
- 告警需要在安全预警页展示和确认。

### 5.10 软件维护

关键对象：

- `SoftwareVersionInfo`
- `SoftwareUpdateRecord`

功能：

- 查看当前软件版本。
- 查看构建时间。
- 查看数据库版本。
- 查看 YOLO 服务版本。
- 查看运行环境。
- 校验离线更新包。
- 后续扩展正式更新、回滚和日志。

## 6. 前端产品结构

### 6.1 首页

首页是生产常驻页面，合并原首页和监控检测页。

保留内容：

- 食品检测：当前食材图像、YOLO 结果图、当前产品/模型/通道。
- 当前图片识别结果：以业务性状展示当前图像的分类数量。
- 分类统计：当前任务累计正常、异常、各缺陷数量和良率。
- 状态记录：传送带速度、累计海鲜数量、工作时长。
- 主控操作台：机器启动/停止、数据源配置、当前状态。

隐藏或弱化内容：

- 原始 YOLO 坐标；
- 剔除命令调试明细；
- 推理开销调试指标；
- 开发者日志。

### 6.2 数据中心

数据中心用于历史统计，不再承担实时监控。

主要对象：

- 海鲜产品；
- 检测任务；
- 缺陷类型；
- 人工复核结果。

主要图表：

- 正常/异常环形图；
- 缺陷数量排行；
- 以检测任务为横坐标的良率趋势；
- 检测任务详情图表；
- 人工复核指标。

### 6.3 设置页

设置页只对管理员开放，按产品设置、硬件设置、剔除设置、系统设置分组。

当前设计原则：

- 产品设置维护产品、模型、通道。
- 剔除设置维护剔除方式和剔除设备参数。
- 硬件设置维护设备本体。
- 系统设置维护安全预警和软件维护。

## 7. YOLO 推理路线

### 7.1 当前路线

当前继续采用 FastAPI YOLO 服务作为推理服务：

- YOLO 服务启动后模型常驻内存；
- 后续请求按模型路径复用模型；
- 保留现有 Python predict 和 phase2 后处理逻辑；
- 支持相邻帧去重；
- 返回检测框、类别、置信度、结果图路径和耗时指标。

### 7.2 为什么暂不直接切 ONNX Runtime

ONNX Runtime 适合最终轻量部署，但当前阶段仍需保留 Python 后处理逻辑：

- 原 Python 代码中包含相邻帧去重；
- phase2 规则仍是模型输出稳定性的关键；
- 算法仍在调整，Python 服务更容易快速迭代；
- 当前系统侧已经通过 FastAPI 实现常驻模型，避免每帧重新加载权重。

### 7.3 标签映射

YOLO 原始输出可能是 `class_0` 或训练标签名称。系统显示时必须转换为当前海鲜产品的业务性状。

转换优先级：

1. 产品层 `LabelMapJson`；
2. 若缺失则回退为模型/原始标签；
3. 最后才回退为 `class_x`。

生产界面不应直接显示 `class_0`。

## 8. 图像数据源与检测任务

### 8.1 X 光相机模式

默认生产模式。

特点：

- 代表真实 X 光探测器或工业相机；
- 机器启动后开始采集；
- 每张图像进入当前检测任务；
- 非正常目标可生成真实剔除命令；
- 硬件异常会触发告警并阻断运行。

### 8.2 本地图片目录模式

离线检测模式。

特点：

- 选择本地图片目录；
- 按固定节拍读取图片；
- 创建检测任务；
- 写入检测记录和统计；
- 不生成、不执行真实剔除命令；
- 可用于算法验证、演示、批量复检。

### 8.3 旧联调入口处理

旧的单张导入、连续目录联调、stream-record 等能力可作为内部调试接口保留，但不应作为甲方功能规格中的主控入口。

主控入口应统一为：

- 数据源配置；
- 机器启动 / 机器停止。

## 9. 剔除控制设计

### 9.1 生产模式

在 `XrayCamera` 模式下：

- 非正常检测结果可生成 `EjectCommand`；
- 根据目标横向位置映射剔除位；
- 根据目标纵向位置、传送带速度、相机到剔除位距离、像素比例和延时补偿计算触发时刻；
- 后续由 `IEjectorController` 对接真实剔除设备或 PLC。

### 9.2 离线模式

在 `LocalImageDirectory` 模式下：

- 非正常目标只记录为异常检测；
- 不生成真实剔除动作；
- 数据中心仍正常统计异常数量、良率和缺陷分布；
- 人工复核仍可使用。

## 10. 硬件接入与告警

### 10.1 建议协议方向

X 光探测器/工业相机：

- 厂商 SDK；
- GigE Vision；
- GenICam；
- Camera Link；
- CoaXPress；
- USB3 Vision。

PLC/设备通信：

- Modbus TCP；
- OPC UA；
- PROFINET；
- EtherNet/IP；
- 厂商私有协议。

### 10.2 抽象原则

业务层不应直接依赖某个硬件厂商 SDK。

建议抽象：

- `IXrayFrameSource`：X 光帧读取；
- `IHardwareSignalSource`：硬件状态信号；
- `IEjectorController`：剔除命令执行；
- `IRuntimeCoordinator`：运行状态协调。

### 10.3 告警目标

核心目标：关键硬件有问题，系统就爆红，并禁止正常运行。

关键告警：

- X 光光源异常；
- X 光探测器离线或采集异常；
- 传送带故障或速度异常；
- 剔除设备故障；
- 控制器/PLC 通信异常；
- 急停或安全联锁触发。

## 11. 人工复核与模型能力评估

当前模型评估采用“异常集合复核”第一版方案。

### 11.1 复核集合

设模型判定为异常并进入剔除集合的目标为 `S`。

复核页面只展示 `S` 中的目标：

- 每个目标一张单目标裁剪图；
- 只保留当前目标红框；
- 不显示其它框，避免干扰人工判断。

### 11.2 可计算指标

- 异常确认率；
- 误检率；
- 类别修正数量；
- 已复核数量；
- 未复核数量；
- 是否完成本次复核任务。

### 11.3 暂不计算严格召回率

严格召回率需要知道漏检数量，即“实际异常但模型未判为异常”的样本数。当前没有对未剔除集合做抽检，因此不能严格计算召回率。

后续可通过以下方式扩展：

- 未剔除集合抽检；
- 低置信目标抽检；
- 人工登记漏检；
- 批次级复核样本策略。

| 报表与追溯未完整闭环 | 当前以数据中心统计和复核为主 |
| 软件更新仍是校验阶段 | 后续需完整离线更新、回滚和日志 |
| 召回率暂不能严格计算 | 当前只复核异常集合，未抽检未剔除集合 |

## 14. 后续路线

### 阶段一：交付展示稳定化

- 统一 WPF HMI 视觉和规格口径；
- 稳定首页数据源配置；
- 稳定数据中心和人工复核；
- 清理旧联调按钮和开发者调试信息；
- 补齐甲方功能规格、用例图、流程图和架构图。

### 阶段二：真实硬件联调

- 接入 X 光探测器；
- 接入 PLC；
- 接入剔除控制器；
- 建立硬件心跳、状态采集和红色联锁告警；
- 完成现场标定。

### 阶段三：生产化增强

- 报表导出；
- 异常图片追溯；
- 批次/班次管理；
- 操作日志审计；
- 软件离线更新和回滚；
- 模型效果长期评估。

## 15. 结论

当前系统已经从“联调原型”推进到“可交付展示的工控机 HMI 软件”阶段。核心方向已经稳定：

- WPF HMI 作为当前交付界面；
- 首页作为生产常驻页面；
- 数据源配置统一生产采集和离线目录检测；
- 产品层管理类别标签文件和业务性状映射；
- 模型只负责权重和版本；
- 通道只负责当前运行绑定和阈值；
- 检测任务作为统计和复核的核心对象；
- 硬件异常必须进入安全预警并阻断运行。

下一步重点不是重新设计架构，而是围绕真实硬件接入、现场标定、告警联锁、复核体验和甲方可见功能规格继续收敛。
